# 依据规格实施

1. 读取用户指定的 change、相关主规格、`design.md`、`tasks.md` 与 `docs/agents/domain.md`。若给的是 GitHub 工作项，读取其完整讨论并找到 OpenSpec 引用。
2. 使用 CLI `status` 与 `instructions apply --change <name> --json` 获取实际任务及项目规则。尚未批准的业务、架构或数据库选择必须先交用户决定。
3. 保护当前分支和未提交内容，在原项目目录实施。不得自动创建分支/worktree、重置已有现场、提交、推送或创建 PR；这些操作仅按用户明确授权执行。
4. 按依赖选择已具备条件的任务，优先复用现有实现和验证入口；每项任务必须形成完整可观察行为，不交付占位代码。
5. 独立且复杂的工作可以按当前助手的委派规则交给子任务；由主助手统一管理，子任务不得继续创建子任务。共享文件、构建与运行资源按项目规则串行处理。
6. 每个行为实际运行验收并检查相关回归；只对观察到完成结果的任务更新 `tasks.md`。服务未部署时不填写已部署。
7. 使用 code-review 核对范围、实现、OpenSpec、文档与证据；修复实际问题后运行对应检查。
8. 所有本次任务完成后，按官方 OpenSpec 同步与归档流程维护主规格和设计记录。授权不足或有未决事项时明确说明，保留真实任务状态。

完成标准：用户批准范围内的全部行为、调用方、规格和正式文档一致，实际验收证据已记录，没有将别人的现场或未验收工作纳入完成声明。
