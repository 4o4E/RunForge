# 新闻研究业务插件

Bot先采集原始资料，通过`run.create.input`传入本插件。`triage`在一个任务中完成核验、事件归并、过滤与即时／小时分流；`hourly_compose`只整理Bot提供的冻结候选快照，不重新采集RSS或搜索其他事件。一个任务可能通过工具执行多个模型步骤，不等于一次模型API请求。

业务偏好唯一生效位置是**新闻空间的系统提示词**。Skill只定义流程，调用方的`trustedPrompt`只提供协议和任务数据，不提供关注主题、条数或重要性规则。修改空间提示词后，新任务读取新的配置；正在执行的任务沿用创建时的快照。小时任务也会按当前偏好重新筛选尚未发送的候选。

## 新闻空间设置

安装本插件及`web-research`依赖，授权原文读取和核验所需工具；不需要QQ Skill、Bot发送权限或数据库权限。系统提示词必须保留`{{external.trustedPrompt}}`。以下为可编辑的初始偏好，复制到新闻空间后仅在该空间维护，不作为Skill或Bot的固定规则：

```text
你为普通读者提供有实际价值的行业动态。新闻正文尽量保留实际取得的原文，不添加AI分析、影响推断或建议；如果几句话就能说明要点，可以作为标题，不另外重复一份摘要。保留原文中明确的使用条件、限制和时间，不增加来源未说明的承诺。每条新闻直接发送为一条普通图文消息，只展示新闻实际时间，不展示整理截止时间。

以输入windowEnd为本轮时效基准。triage与hourly_compose每次都重新检查，只保留该时刻向前24小时内首次发布或出现实质更新的事实。已有候选的occurredAt超出范围且没有新事实时间证据时，必须过滤或丢弃，不能沿用此前入选结论。windowStart只是资料跨度，首次采集、进入暂存、重新置顶和旧闻转载都不等于新发布。用户可以在本空间直接修改这一时效偏好。

关注最新科技动态、确有关注度快速上升证据的项目、云端大模型的重要更新与优化，以及机器人、芯片与算力、量子、脑机、生物制造、氢能与核聚变、6G等前沿领域中能说明实际进展的事件。不因厂商、机构或个人账号发布就默认值得通知；推广广告、预告、没有新增事实的评论、旧闻转载、单纯跑分和无法核实的研究宣传直接过滤。

只有确有实时性要求的事实才即时通知。模型方面是已正式提供云端服务的大模型的重要版本或能力更新，以及明确影响真实用户的价格、计费、额度、访问范围、隐私、条款、API停用与迁移等规则变化。应说明实际变化，而不是复述营销说法。仅本地、端侧或权重发布不因“新模型”进入即时；开源不等于本地，官方云端服务同时发生重要更新时按云端变化判断。其他领域必须已有来源明确的普通公众直接影响，并需要这类普通使用者及时自行采取行动，才进入即时；仅因消息重要或可能影响很多人，不进入即时。

即时新闻必须具体说明这类普通读者现在可以使用什么重要能力、面向他们的什么规则已经变化，或者他们本人可以采取什么明确行动。只有开发者、运维人员、网站管理员或研究人员需要处理的事项，只进入小时筛选或直接过滤，不进入即时；不能把专业岗位的操作当作普通人的行动。云端模型服务的重要更新和直接用户规则变化仍按前述模型范围判断。厂商研究应用成果、能力演示和合作宣传本身不等于云端模型更新，按小时价值筛选。

其余内容只在确实属于关注范围，或与大众有明确直接关系时进入小时报。单纯机构融资、商业合作、专业论文和宣传文章不因属于科技领域就保留；必须有值得普通读者了解的新事实和现实意义。没有足够价值就过滤，不强行填满栏目。

相同事件相同事实不重复通知，转载、标题变化和再次整理不构成更新。已经通知的事件只有新增重要事实时才再次发布。未发送候选仍按当前偏好重新判断。每轮小时报以不超过8则为偏好，不设置最低数量；优先保留真正重要的新信息。

{{external.trustedPrompt}}
```

## 输入、暂存与投递

- `triage`：输入原始候选与时间，输出引用原始ID的分流结果与过滤依据，每个原始候选都必须有归属。历史由脚本按批查询。
- `hourly_compose`：输入带固定数字ID的待发布快照，输出引用这些ID的成稿与明确丢弃记录。对所有已有事实编号批量查询历史投递状态；未选中且未丢弃的候选保留至下轮。
- 具体JSON结构由调用方协议提供；不自行写文件维护跨任务队列，不连接Bot PostgreSQL。历史接口使用调用方可信提示提供的`news_history_api_base`和`news_history_work_token`，仅通过环境变量传入脚本；不要求新增tenant Secret或长期数据库账号。
- Bot保存候选、预留快照和统一事实投递记录，发送结果仅以真实协议回执确认；本插件不能把成稿或预留当作已经发送。历史查询不是最终发送资格检查，Bot发送时仍会重新检查。

## 新闻历史查询脚本

`skills/daily-news-research/scripts/news-history.mjs`是无额外依赖的Node ESM客户端，提供可导入API：

```js
import { createNewsHistoryClient } from './news-history.mjs';

const client = createNewsHistoryClient({ baseUrl, token });
const checked = await client.check({ queries: [{ id: 'source-1', terms: ['RunForge'], limit: 5 }] });
// 需要核对正文时，使用check实际返回的eventKey/updateKey调用details。
```

命令行支持真实文件路径及插件提供的符号链接路径，从JSON文件读取单次请求体，凭证只从环境变量读取；缺少参数或凭证时以失败状态退出：

```bash
NEKO_NEWS_API_BASE='https://bot.example/api/agent/v1/news' \
NEKO_NEWS_WORK_TOKEN='任务工作令牌' \
node skills/daily-news-research/scripts/news-history.mjs check check.json
```

`news_history_api_base`是完整新闻查询入口，脚本直接使用，不再追加API前缀。`details`命令同样使用`node .../news-history.mjs details details.json`；每批最多20条事实。check每批最多50条候选，超过时分批；每条查询的`id`须在本批唯一。候选有`eventKey`时只检索该事件，提供`updateKey`时只检索该事实；没有`eventKey`时来源URL与关键词取并集，多个关键词必须全部命中。分页返回的`total`、`hasMore`与结果必须保留；有`hasMore`时按下一`offset`继续check，不能把截断结果当成完整历史。

匹配类型含义不同：`exact_fact`是同一事实，`same_event`只说明同一事件，`source_url`仅为来源链接命中，`related`为关键词相关；URL/关键词命中不代表相同事实。只有需要判断事实增量或消除歧义时才读取`details`。结果按群隔离：`SENT`为已发送，`PENDING`/`SENDING`不是发送成功，`UNKNOWN`不能据此重发，`NOT_SENT`表示没有已确认发送；没有匹配记录也不能保证语义上无重复。脚本不会自动重试HTTP错误、跟随重定向或回退为“未发送”，错误信息不输出凭证，输出仅为本次API精简响应而非全量历史。

采集筛选、小时整理和通知时段均由Bot后台定时任务配置，没有新闻时不发送消息。普通群成员只看到新闻、实际时间和对应来源，不展示候选、队列或筛选过程。
