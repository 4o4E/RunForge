# 领域文档

## 开始调查或设计前

1. 读取根目录 [GLOSSARY.md](../../GLOSSARY.md)，使用其中术语。
2. 读取相关 [OpenSpec 能力规格](../../openspec/specs/) 与活动变更；涉及架构时读取相关活动或归档变更的 `design.md`。
3. 按主题进入 `docs/` 的现行协议与实现解释；早期方案或阶段日志不能覆盖现行规格。

## 写入位置

| 内容 | 写入目标 |
| --- | --- |
| 经用户确认的领域名称与定义 | `GLOSSARY.md` |
| 变更的目标和非目标 | `openspec/changes/<change>/proposal.md` |
| 需求和可观察场景 | 该变更的 `specs/<capability>/spec.md` |
| 架构选择、确认状态、原因、代价与替代关系 | 该变更的 `design.md` |
| 实施、依赖和验收 | 该变更的 `tasks.md` |
| 已完成行为 | 同步后的 `openspec/specs/<capability>/spec.md` |

这是全部工程技能的项目约定，适用于 domain-modeling、设计讨论、问题诊断、规格生成、分工、实现、测试与审查。OpenSpec 的 `design.md` 承担架构决定记录，技能直接读取和更新它；不建立独立 ADR 正文。当前各包共享同一领域语言，不按包复制术语表。

## 决定与规格冲突

发现提案与既有规格或已确认决定冲突时，给出具体用户场景、原决定来源与影响，等待用户确认；新决定在新 change 中引用并替代原决定。已归档 design 保持原文，主规格通过 delta 更新，不把未批准提案当作现行事实。

只有难以更改、缺少理由会使后续读者困惑、且确实经过方案选择的决定才需要长期记录。术语只记录名称与业务含义，不包含实现细节或任务进度。
